# 설계 절차 (architect)

목표는 문서를 길게 쓰는 것이 아니다. **implementer가 중요한 기술 결정을 스스로 내리지 않아도 구현할 수 있게** 모호함을 없애는 것이다.
해당하지 않는 항목은 쓰지 않거나 "해당 없음: 이유" 한 줄로 둔다.

## 깊이
`sched next --pool design`의 `design_depth`를 따른다(없으면 standard).

| 깊이 | 쓰는 곳 | 반드시 쓸 것 |
|---|---|---|
| light | 범위가 분명한 작은 변경 | 바꿀 파일·인터페이스, 영향 범위, 주요 경계·오류 조건, 테스트 방법 |
| standard | 일반 기능, 여러 모듈 연동 | light + 대안 비교(채택·기각 이유), 모듈 책임과 의존 방향, **공개 인터페이스 계약**, 데이터 모델, 데이터 흐름, 오류 처리, 호환성, 작업별 담당 경로 |
| deep | 핵심 구조, 공통 계약, 복잡한 알고리즘, 데이터 무결성·보안이 중요한 것 | standard + `references/deep-checklist.md`의 해당 항목(상태 전이, 동시성·트랜잭션, 장애·복구, 보안·신뢰 경계, 비기능 목표, 마이그레이션) |

## design.md 형식
`docs/asterbraid/design/YYYY-MM-DD-HHMM-<작업 ID>.md` 하나가 기본이다(이 문서에서 design.md라 부른다). 첫머리에 작성 시각·작업 ID·깊이.
길어지면 같은 폴더에 `…-<작업 ID>-contracts.md` 등으로 나누고 본 문서에서 잇는다.

```markdown
# <작업 ID> 설계 (깊이: standard)
## 요구사항과 범위
- 충족할 완료 기준(그대로), 범위 밖, 아직 정해지지 않은 것(사용자 결정 필요 → manager에게)
## 결정
| 결정 | 채택 | 기각한 대안과 이유 |
## 구조
- 모듈별 책임, 의존 방향(누가 누구를 부르는가), 공통 계약의 소유 모듈
## 계약 (implementer가 그대로 따른다)
- 함수·API: 이름, 입력(타입·필수·기본값·범위), 출력, 오류(언제·무엇을), 부수 효과, 멱등성
- 데이터: 필드·타입·단위·NULL의 뜻, 식별자, 불변 조건(항상 참이어야 하는 것)
## 실패와 경계
- 잘못된 입력, 빈 값, 중복, 외부 실패 때 동작
## 작업 분할
| 작업 | 구현할 계약 | 담당 경로 | 선행 작업 | 테스트 기준 |
## 테스트
- 요구사항 → 테스트 이름(또는 검사 방법) 대응
```

## 규칙
- 계약은 성공 경로만 쓰지 않는다. 오류·경계 동작이 없으면 implementer마다 다르게 만든다.
- 여러 작업이 쓰는 계약(API, 스키마, 타입)은 그 계약에 기대는 작업보다 먼저 확정한다. 코드로 먼저 정의해야 하면 선행 작업으로 제안한다.
- 측정하지 않은 성능 수치를 사실처럼 쓰지 않는다. 필요한 목표와 측정 방법을 쓴다.
- 요구가 없는 추상화·확장점을 넣지 않는다. 빠르다는 이유로 계약을 비워 두지도 않는다.
- 사용자가 정할 것(제품 방향, 호환성을 깨는 변경, 새 의존성)은 정하지 말고 질문으로 보고한다.
- UI가 있는 작업이면 화면이 약속하는 동작이 계약과 맞는지 적는다(미리보기와 다른 계약을 만들지 않게).

## 끝내기 전 점검
중요한 요구사항이 모두 계약·테스트에 이어지는가 / 모듈 책임이 겹치지 않는가 / 계약끼리 충돌하지 않는가 /
오류 동작이 정해졌는가 / 두 implementer가 따로 읽어도 같은 것을 만들겠는가 / 아직 남은 결정은 무엇인가.

## 보고 (manager에게)
요약, 노트 경로, 제안하는 작업 분할과 의존(`--deps`), 사용자 결정이 필요한 항목.
